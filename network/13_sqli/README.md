# 13 · SQL 注入全流程：union 拖库、盲注信道与 sqlmap 对照

> SQL 注入（把用户输入当代码执行的漏洞）常年位居 OWASP Top 10（Web 应用
> 十大风险榜单）前列。本实验把全流程打一遍：union（把别的查询拼进原查询
> 一起显示）一次拖出全部账号口令、布尔与时间两条
> 盲注信道、五点迷你检测器（含对照点）、sqlmap 对账，以及一行修复的
> 参数化对照。所有攻击只打本实验的本地 DVWA 靶场。

## Background

SQL 查询本该是「模板填空」：`SELECT ... WHERE user_id = ?`，用户只提供
填空内容。但大量代码把用户输入直接拼进语句——输入 `1' OR '1'='1` 时，
数据库看到的已经不是数据，而是被改写过的**代码**。

后果分三层：能直接回显查询结果时（union），一次请求拖走整张表；没有
回显只有真假差异时，用布尔盲注一个 bit 一个 bit 问；连差异都没有时，
还能用「响应时间」当信道。DVWA 的 sqli / sqli_blind 模块与四档安全
等级，就是把这三种场景逐级摆出来的标准教具。

## What

一句话定义：SQL 注入是**通过操纵输入让数据库执行攻击者构造的语句**，
而注入器（含 sqlmap）是把「构造 → 验证 → 提取」自动化的工具。

心智模型：把 SQL 语句想象成一张填空题卷子——正常用户只在横线上写字，
注入是在横线里塞进「翻页指令」，让整张卷子按攻击者的意思继续答下去。
失效边界：注入能走多远取决于数据库权限——只读账号与 DBA（数据库管理
员，最高权限）账号是两个世界（本实验账号权限很大，是靶场的刻意设置）。

三条信道的成本对照（本实验都会实测）：

| 信道 | 适用条件 | 成本 |
|:---|:---|:---|
| union 回显 | 查询结果会显示在页面上 | 1 个请求拖全表 |
| 布尔盲注 | 页面有真假差异、无回显 | 约 7 请求/字符（ASCII 二分） |
| 时间盲注 | 连差异都没有 | 1 次 SLEEP（数据库延时函数）/询问，秒级/字符 |

## When to Use

典型场景：授权渗透中验证注入点并证明影响；代码审计时快速确认「拼接
SQL」的风险面；给实验 19 的日志审计制造真实的注入流量样本。

何时不用：未授权目标不碰；量级上别用 sqlmap 的默认并发去打生产——
它很吵，WAF 与限流会立刻盯上你；静态扫描能发现的拼接代码，优先在
代码层修复而不是打进去。

| 方案 | 机制 | 什么时候选它 |
|:---|:---|:---|
| 手工注入（本实验） | 按响应类型选信道 | 看清原理、精确控制 |
| sqlmap | 自动化检测与拖库 | 已确认注入点后的批量提取 |
| 静态扫描（SAST） | 读源码找拼接点 | 左移（把安全提前到开发阶段）修复 |

## How It Works

![SQL 注入的三种问法](images/sqli_lab.svg)

> 怎么看：从左到右是「探针 → 三种问法（回显 / 布尔 / 时间）→ 修复」。
> 每种问法下面写着它的信道与成本；虚线边表示「上一条路走不通时的
> 退路」，最后的参数化查询把三条信道一并封死。

> 🌐 **交互版**：本地打开 [`images/sqli_lab.html`](images/sqli_lab.html)。

**定列数是一切的前置**：`ORDER BY n` 逐级加大会在超列时触发 SQL 错误
——本靶场的报错信号是**空响应**（页面主体为空），于是 2 列在第三个
试探就暴露了。接着 `UNION SELECT 1,2` 找到会显示在页面上的「显位」。

**布尔盲注：把数据库名变成一串「是/否」问题**：`ASCII(SUBSTRING(database(),1,1))>64`
——真/假直接体现在页面内容上；二分查找每字符最多 7 个请求（95 个可打印
字符的对数）。本实验 4 个字符实测 0.2 秒，比人翻页还快。

**时间盲注：没有任何回显差异时的最后信道**：`... AND SLEEP(1.5)=0`，
实测延迟 1.5 秒；再用 `IF(条件, SLEEP(1.2), 0)` 把「某字符是否等于 X」
编码成时间。慢，但它证明了一件事——**只要查询执行了，就总有信道**。

**五点检测器**：同一套三探针（布尔差异 / 时间延迟）打 4 个注入点
（sqli 与 sqli_blind × low/medium），外加 1 个对照点（参数没被用于查询
的页面，必须判「安全」）——只报真阳性、不误伤，才配进报告。

**sqlmap 对账**：把会话 cookie 喂给 sqlmap，`--dump -T users` 拖出的
口令 hash 与手工 5 行逐字相同。它不证明 sqlmap 神奇，只证明一件事：
工具是把你学会的思路自动化了——读懂它的输出，才谈得上用好它。

## Pitfalls & Q&A

踩坑清单（现象 → 原因 → 解法）：

- **medium 点误判安全**：表单改用 POST 提交了——检测器需按档位切方法。
- **union 只出 1 行或直接空响应**：列数与显位没对齐——ORDER BY 试探 +
  占位符（NULL/数字）逐列对齐。
- **SQL 报错页面是空的**：本靶场限制了错误显示——把「空响应」当报错
  信号即可。
- **sqlmap 跑得慢**：首次探测每种注入技术都要试——`--flush-session`
  后的全量探测约 1 分钟属于正常。

深入问答：

- **Q: 布尔盲注为什么是 7 请求/字符？** A: ASCII 打印字符约 95 个，
  二分查找 log₂95 ≈ 7 次比较定一个字符；时间盲注同理但每次要等 SLEEP。
- **Q: 有 WAF 了还需要学这个吗？** A: 需要——WAF 绕过（大小写/编码/
  注释变形）是下一层博弈；本实验建立的是「信道与原理」的地基。
- **Q: 为什么检测器要包含对照点？** A: 只抓真阳性的检测器才有报告
  价值；误报（把安全页面判成注入）会让蓝队疲于奔命，这也是实验 19
  告警规则的同一课。
- **Q: 参数化为什么能一劳永逸？** A: 它把「代码」与「数据」在协议层
  就分开——参数先作为纯数据传给数据库，之后才参与查询，天然不可注入。
