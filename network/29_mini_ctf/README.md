# 29 · 自建 mini-CTF：六关串联全方向

> 收官前的综合考：一个 flask 单文件平台（判分 + 计分板）挂出六道题——
> 套娃编码 / MD5 弱口令 / SQLite 注入 / XSS 偷 cookie / 日志取证 / 逆向
> crackme。官方解题器全程模拟选手：**六关全解、逐题判分通过、计分板
> 750/750**，每题附 writeup（解题过程）。这一节同时做两件事：当出题人
> （设计题目与判分规矩），当选手（写解题器把每关打通）。

## Background

前二十八课分散在各方向：扫描、注入、XSS、取证、逆向、防御…… CTF
（Capture The Flag：解题与攻防对抗的竞赛）是安全学习的「统一考场」——
把散落的技能串成一条可判分的考核线。

出题视角还多一层价值：设计一道「好题」逼你把自己会的东西讲到别人
能做对——这是对掌握程度最诚实的检验。

## What

一句话定义：**mini-CTF = 把学过的知识做成可判分的题目与解题过程**。

心智模型：CTF 像一份「诊断考卷」——每道题给你一个不完整的世界（一段
密文、一张登录页、一份日志），flag 是唯一正确答案。

失效边界：本平台是本地单人的教学版（无账号、无防作弊、无并发与动态
flag）；真实 CTF 平台要隔离题目、限频提交、防 flag 共享——但「题面 →
解题 → 判分」的最小闭环完全一致。

| 题目 | 考什么 | 前置实验 |
|:---|:---|:---|
| ① 套娃编码 | 分层解码（判层/辨型） | 7–9 |
| ② MD5 弱口令 | 词典碰撞 | 7 |
| ③ SQLite 注入 | 字符串拼接绕过 | 13 |
| ④ XSS 偷 cookie | 存储型 XSS（跨站脚本：输入被当脚本、在访问者浏览器里执行；先存服务器、打开页面才触发）+ 机器人（bot：自动开页面的模拟访客） | 14 |
| ⑤ 日志取证 | URL 编码外带定位 | 19 |
| ⑥ 逆向 crackme（答对口令才打印 flag 的练习二进制） | XOR（异或运算）混淆的静态还原 | 24 |

## When to Use

典型场景：自测学习成果（六关全绿=前几个阶段的手感还在）；给同学出题
（出题是最好的复习）；阶段验收时把技能「考试化」做自检。

何时不用：想练真实攻防请回到 DVWA（Damn Vulnerable Web Application：故意
留漏洞的演练靶站）等靶场（判分制会诱导「对着答案练」）；不是「刷题就变强」——writeup 才是，讲不清的等于没学会。

| 做法 | 机制 | 什么时候选它 |
|:---|:---|:---|
| 刷题平台（真实 CTF） | 题库 + 排行榜 | 检验广度与速度 |
| 本 mini-CTF | 出题 + 判分 + writeup | 检验「能否讲明白」 |
| 靶场实战 | 完整业务环境 | 练杀伤链（从侦察到得手的攻击步骤链）与工具链 |

## Quick Start

前置：宿主 python3（flask + requests）；node + puppeteer-core（驱动无头 Chrome（headless：无窗口后台运行）的
Node 库；机器人=自动打开留言页的模拟管理员；复用系列 node_modules）；Docker（编译 crackme）。

```bash
cd network/29_mini_ctf
./ctf_lab.sh            # 起平台 → 六关全解并提交 → 计分板与 writeup 核验（约 15 秒）
./ctf_lab.sh apply      # 只编译 crackme 并启动平台
./ctf_lab.sh observe    # 只跑四步观察（需先 apply）
./ctf_lab.sh clean      # 停平台并清产物（crackme 重建秒级）
```

## How It Works

![六关一平台：从解题到计分的一条流水线](images/mini_ctf.svg)

> 怎么看：上排主链——平台启动 → 选手闯六关 → flag 判分 → 计分板 →
> writeup 归档；下排是第 ④ 关的真实加演：留言被上报后，管理员机器人
> 带着 cookie 来访，注入脚本在浏览器里外带数据。

> 🌐 **交互版**：本地打开 [`images/mini_ctf.html`](images/mini_ctf.html)。

**出题视角：flag 藏哪**：①藏在编码洋葱的多层（考判层与辨型）；
②藏在字典与摘要的缝隙（考碰撞）；③藏在拼接 SQL 的引号外（考注入）；
④藏在别人的浏览器里（考 XSS 与外带）；⑤藏在日志的一行 URL 里（考
解码与定位）；⑥藏在混淆的字节里（考静态还原）——六种藏法，六种考法。

**判分与计分板**：三条规矩——首解计分、重提 already、错旗 wrong；
每次计分追加「题号 + 分数 + 时间」并写进 scoreboard.json（平台崩了
分数还在）。计分板不是装饰：它是验收「判分正确」的证据面。

**XSS 关为什么是真的**：机器人不是模拟脚本——无头 Chrome 真带
`admin_session` 打开留言页，`onerror` 外带脚本在浏览器里执行，
`document.cookie` 被真实发送到收集器。「注入 → 触发 → 外带 → 截获」
与现实攻击同构。

## Pitfalls & Q&A

踩坑清单（现象 → 原因 → 解法）：

- **机器人把平台卡住**：flask 开发服务器需 `threaded=True`——机器人在
  来访时平台还要响应它取页面/外带的请求，单线程必死锁。
- **重复提交的判定顺序**：先判旗后判重复——否则已解题目收到错旗会
  误答「already」（开发时被验收脚本抓过现行）。
- **平台重启丢分**：状态只存内存 → 每次计分立刻落盘 scoreboard.json。
- **kill 后台进程的作业通知**：bash 会打印带 PID 的「Terminated」——
  破坏「两跑逐字一致」，用 `disown` 把平台移出作业表。

深入问答：

- **Q: 为什么 flag 是固定串而不是每局随机？** A: 教学判分要稳定、要能
  与 writeup 逐字对账；真实赛事建议动态 flag（防共享）——这是教学版
  与生产版的公开差异。
- **Q: 出题最难在哪？** A: 「难而不犟」——解法要唯一可推理、验证可
  复现；卡在猜谜的题不是好题。
- **Q: 哪关含金量最高？** A: ④：其它关是静态数据或服务端逻辑，只有
  它走通了「真实浏览器执行不可信脚本」的完整链路。
