# 01 · 多线程 TCP 端口扫描器：connect 探测、banner 抓取与 nmap 对照

> 端口扫描是资产测绘第一步——机器开着哪些 TCP 端口（TCP 是传输控制协议，
> 先建连接再传数据的网络协议），决定攻击面有多大。本实验用约 160 行标准库
> 代码实现多线程端口扫描器，跑通「起服务 → 扫描 → banner 抓取 → nmap 对照
> → 限速 → 清理」全流程。命令只针对 127.0.0.1，勿扫未授权目标。

## Background

在没有扫描器之前，确认一台机器开了哪些端口，只能靠 `telnet 主机 端口` 或
`nc -z 主机 端口` 一个个手工试。

这种方式撞上两堵墙：数量上，65535 个端口逐个试要近两小时；信息上，被防火墙
静默丢弃的端口不会立刻回绝，只能干等超时，无法区分「关闭」和「被过滤」。

1997 年 nmap（Network Mapper，网络映射器）把「并发探测 + 结果分类 + 服务
识别」做成标准工具。本实验复刻它的最小内核：socket（网络连接编程接口）
连接、线程池（预建一组线程、任务排队领取）并发、按响应分类端口，再抓服务
banner（服务连接后吐出的自我介绍）。

## What

一句话定义：端口扫描器是**对目标的一串 TCP 端口逐个发起连接、按响应分类为
open / closed / filtered 的工具**。

心智模型：把目标主机想象成一栋走廊两侧全是门的楼，扫描就是挨个拧门把手——
拧开了是 open，转不动是 closed，敲门毫无回应、等到超时的是 filtered
（被防火墙丢弃）。但和现实不同的是：门的总数固定（1-65535），而且你拧过的
每一扇门都会在对方日志里留下记录，并不隐形。

三分类的线上语义：

- **open**：TCP 三次握手（SYN → SYN/ACK → ACK 三步建连）完成，有服务监听。
- **closed**：对方回 RST（reset，明确的拒绝复位包），可达但没有服务。
- **filtered**：完全无响应直到超时，通常是防火墙丢包（本实验归入「未开放」）。

## When to Use

典型场景：

- 资产盘点与信息收集：对授权范围主机先扫出开放端口，再决定深挖哪些服务。
- 渗透测试：针对已授权目标，用端口结果定位 Web、数据库等入口。
- 验证加固效果：改完防火墙规则后复扫一遍，确认暴露面确实缩小了。

何时不用：未授权的目标一律不能扫；同一目标高频全端口扫描会触发对方
IDS（Intrusion Detection System，入侵检测系统）告警，等于开灯行动。

同类方案对比：

| 方案 | 机制 | 什么时候选它 |
|:---|:---|:---|
| TCP connect 扫描（本实验） | 完整三次握手，普通 socket 即可 | 学习原理、本地与授权环境的常规探测 |
| SYN 半连接扫描 | 只发 SYN 不回 ACK（需 root 原始套接字） | 需要隐蔽、不留应用日志的场合（nmap -sS） |
| UDP 扫描 | 无连接协议，靠 ICMP 差错消息判断 | 探测 DNS、SNMP 等 UDP 服务 |
| masscan | 自造 TCP/IP 栈，异步发包 | 全网段、全端口级别的超大规模扫描 |

## Quick Start

前置：macOS + Homebrew 的 python3（只用标准库）；nmap 可选（装上自动对照，
`brew install nmap`）。

```bash
cd network/01_tcp_port_scanner
./tcp_port_scanner.sh            # apply → observe → clean 一条龙（约 6 秒）
./tcp_port_scanner.sh apply      # 只起靶场：127.0.0.1:8000 的 HTTP 服务
./tcp_port_scanner.sh observe    # 只跑扫描、断言、nmap 对照与限速演示
./tcp_port_scanner.sh clean      # 停靶场，端口复原
```

observe 阶段的真实输出（节选，端口打印顺序随线程调度略有不同）：

扫描器也可独立运行：`python3 port_scanner.py 127.0.0.1 -p 1-10000 -t 100`（支持区间与逗号混写，`--rate 50` 全局限速）。

诚实预期（新手第一个失败点）：apply 报「靶服务 4 秒内未就绪」说明 8000 被占用：
`lsof -i :8000` 查占用者或 `LAB_PORT=9001 ./tcp_port_scanner.sh` 换端口重跑。
另一个「看起来失败」的现象：扫本机会连 macOS 系统服务一起扫出来——正常。

## How It Works

![TCP connect 扫描流程](images/tcp_port_scanner.svg)

> 怎么看：主线程解析参数生成端口列表，丢进线程池；100 个工作线程各自走
> 「connect 判定 → banner 抓取」循环，只有 open 会带着 banner 进入结果集。

> 🌐 **交互版**：本地打开 [`images/tcp_port_scanner.html`](images/tcp_port_scanner.html)。

**connect_ex() 为什么是判定核心**：每个端口先建一条 socket 连接对象（代码
里的 `s`）；`connect_ex` 是 connect 的「不抛异常版」直接返回错误码，用来
三分类——`8000/tcp open` 那一行就来自它的返回值，closed/filtered 被丢弃，
只打印开放端口：

```python
s.settimeout(timeout)
if s.connect_ex((ip, port)) != 0:     # 非 0 即没握上手：RST=closed，超时=filtered
    return None
return port, grab_banner(s, port, timeout, ip)   # 握手成功就留着 socket，立刻用它抓 banner
```

**为什么线程池够用**：扫描是 I/O 等待型任务，等网络响应时 Python 会释放 GIL
（全局解释器锁，同一时刻只允许一个线程执行字节码的机制），100 个线程因此能
真正并发地等；实测 10000 个端口 0.9 秒。

**banner 抓取**：SSH、FTP 连上后会主动推送 banner，被动 `recv()` 就能拿到；
HTTP 服务要客户端先说话，所以对常见 HTTP 端口补发 `HEAD / HTTP/1.0` 再读响应，
输出里 `Server: SimpleHTTP/0.6 Python/3.10.20` 就是它。

**限速器怎么工作**：`RateLimiter` 维护「下一个允许出发的时刻」，线程探测前
先取号：算好自己该等多久，同时把下一个号推后。20 次/秒的实测是 21 个端口
耗时 1.01 秒：首个探测立即出发，其余 20 个各隔 1/20 秒 ≈ 1 秒。限速能避免
打满对方的连接表、也降低被 IDS 标记的概率。

## Pitfalls & Q&A

踩坑清单（现象 → 原因 → 解法）：

- **apply 报「靶服务 4 秒内未就绪」**：8000 被占用。`lsof -i :8000` 找到
  占用者，或 `LAB_PORT=9001 ./tcp_port_scanner.sh` 换端口重跑。
- **扫出的端口比预想多**：本机系统服务都在监听，和 `nmap` 对照一致即可确认准确。
- **远程目标扫不到东西、全是超时**：0.5 秒默认超时只适合本机与局域网；
  公网目标用 `-T 2` 放大超时，总耗时也会随之上升。
- **banner 是 `-`**：服务既不主动说话、又不在 HTTP_PORTS 探测清单里；
  按需把端口加进 `HTTP_PORTS`，或为其他协议扩展主动探测。

深入问答：

- **Q: 为什么 connect 扫描「吵」？** A: 它完成整个三次握手，Web 服务器会把
  它记进 access.log；SYN 半连接扫描不发最后 ACK，应用层看不到连接建立。
- **Q: 把线程数拉到 1000 不是更快？** A: 收益递减且风险上升——大量并发会
  耗尽临时端口（系统为连接分配的本地端口），100~200 是本机局域网的甜点区。
- **Q: closed 和 filtered 在工具眼里有什么区别？** A: closed 收到 RST 秒回，
  filtered 等到超时才判定；与 nmap 对比时只有 open 状态的端口参与检查。
- **Q: 这个扫描器能拿去做真实渗透吗？** A: 技术上它能扫任何可达主机，但只
  允许用在授权范围内——这条边界就是安全学习与违法行为的分界线。
