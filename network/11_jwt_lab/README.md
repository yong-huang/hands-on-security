# 11 · JWT 安全实验室：none 伪造、弱密钥爆破与算法混淆

> JWT（JSON Web Token，签名的 JSON 声明）常被当作登录凭证——「签名对了就
> 可信」是它的全部安全承诺。但三种实现薄弱方式能让伪造绕过签名。本实验起
> 三个靶（漏洞实现 / 弱密钥 / 正规实现），用三种真实攻击逐一验证：攻破、
> 爆破、三连拒。全部目标为本实验自建靶站。

## Background

传统登录用服务端会话：服务器存一份「谁登录了」的状态，浏览器只拿一个
随机 session id。服务一多，共享状态就成了负担（跨服务、跨机房都要查同一
份存储）。

JWT 换思路：把状态放进 token 本身交给客户端保管，服务端只验签名——
无状态、跨服务天然可用，因此被广泛采用。但安全承诺全部押在「签名」上：
payload（负载）只是 base64url（Base64 的 URL 安全变体：+ / 换成 - _、
去掉补位 =）编码的明文，谁都能读；防篡改完全依赖签名验证。

问题就出在「怎么验」。历史上公开过一串真实漏洞：none 伪造（alg 标成
none——自称「无签名」）、HS256 弱密钥（HMAC-SHA256：签名与验签共用同一
把密钥，密钥一猜中就能自签）、RS256→HS256 算法混淆（诱导服务端按攻击者
选定的算法验签）——全部源于实现细节，而不是算法本身。

## What

一句话定义：JWT 是**由「头部 + 负载 + 签名」三段组成的签名凭证**，
服务端通过验证签名来确认声明未被篡改。

心智模型：JWT 像一封盖了防伪印章的介绍信——头部是信封上的说明（用哪种
印章）、负载是明文信文、签名是印章本身。验证方只认印章：印章对不上就是
伪造。失效边界：签名只回答「没被改过」，不回答「内容是否正确、是否过期、
权限够不够」——认证与授权是两件事。

本实验的三靶三攻：

| 靶站实现 | 对应攻击 | 结果 |
|:---|:---|:---|
| 信任 token 自称的算法（漏洞） | none 伪造（签名段留空） | 攻破，拿到 admin 响应 |
| HS256 + 6 字符纯小写密钥 | 字典爆破（离线验签） | 0.00s 命中 `secret` |
| 固定算法白名单 + RS256 | 三种攻击全部失败 | 三连拒（none/confuse 返 401 + 爆破未命中） |

## When to Use

典型场景：实现登录凭证与服务间身份传递（微服务里「我是谁」的通行证）；
接入 OAuth2/OIDC 生态（两套常见的授权与身份协议，access token 多为 JWT
形态）；看懂「为什么后端要校验每一段 token」的问题工单。

何时不用：不要把敏感数据放进 payload——它只是编码不是加密；需要即时
吊销时 JWT 的无状态特性反成负担（要么短 TTL + 刷新，要么加黑名单）。

| 方案 | 机制 | 什么时候选它 |
|:---|:---|:---|
| JWT（本实验） | 自包含签名凭证 | 无状态、跨服务、生态通用 |
| 服务端 session | 状态存服务端 | 单体应用、需要即时吊销 |
| OAuth2 不透明 token | 内容不可见，查 introspection（自省接口） | 想让 token 完全不携带信息 |

## How It Works

![JWT 攻击面 vs 三种验签实现](images/jwt_lab.svg)

> 怎么看：上中下三条线是「攻击 → 靶站实现 → 判定」。两条翻车线（信任
> header 算法、弱密钥）分别通往「攻破」与「密钥到手」；底部的正规实现
> 让三种攻击全部失败（none/confuse 得 401，爆破未命中）。

> 🌐 **交互版**：本地打开 [`images/jwt_lab.html`](images/jwt_lab.html)。

**三段结构**：`header.payload.signature`，各段是 base64url 编码。头部
自称算法（`alg` 字段）、负载是明文声明、签名则是 HMAC（共享密钥的认证码）
或 RSA（私钥签、公钥验）对前两段盖章。payload 谁都能解：`base64 -d` 即可
读到 `role`。

**漏洞一：把「自称」当「事实」**。vuln 靶按 token 头部自称的算法验签，
于是攻击者把 `alg` 改成 `none`、签名段留空，就得到一张「合法」的 admin
token。正路是服务端**写死算法白名单**——token 自称什么都不理。

**漏洞二：密钥短到字典可枚举**。弱靶的 HS256 密钥是 `secret`。爆破脚本
拿到任意一个合法 token 后离线试字典：验签 == 本地算 HMAC 对比，无网络、
无锁定，18 词 0.00s 见底。密钥长度与随机性的下限，就是攻击成本的上限。

**漏洞三：算法混淆**：服务端用公钥验 RS256 没错，但若实现允许「降级到
HS256」，攻击者就把公开拿到的**公钥文本**当 HMAC 密钥重签 token——服务端
若用同一串文本当 HMAC 密钥，签名就「对上了」。本实验强靶写死 RS256，
混淆直接吃 `InvalidAlgorithmError`。

**强靶三件套**：算法白名单 + 非对称签名（公钥公开也不怕）+ 角色校验
（合法 alice token 访问 /admin 是 403——认证通过 ≠ 授权通过）。

## Pitfalls & Q&A

踩坑清单（现象 → 原因 → 解法）：

- **现代库拒绝 none**：PyJWT 2.x 直接抛错——漏洞靶因此手写解析；生产
  代码不要模仿，模仿的正是它的「漏洞演示」身份。
- **爆破目标选错**：字典爆破只对共享密钥（HS256 类）有效；RS256 靶跑
  字典自然「未命中」，这不是脚本出错。
- **端口占用的排障**：`lsof -i :8501` 查占用者，或 `LAB_PORT=8511
  ./jwt_lab.sh` 把三靶整体平移。
- **别在生产 payload 里放敏感字段**：email、手机号都在其中明文可读。

深入问答：

- **Q: JWT 能做「注销」吗？** A: 无状态 token 发出后收不回来——常用
  组合是短有效期 + refresh token（续期用的长期凭证），或用黑名单（这又
  引入了状态，权衡使然）。
- **Q: 为什么 payload 明文还敢用？** A: JWT 的设计目标是「防篡改」不是
  「防偷看」；需要机密性就整体再加一层加密（JWE）。
- **Q: 算法混淆在真实项目里长什么样？** A: 常见于「根据 token 头选验签
  方式」的通用中间件与旧 SDK；修复只有一句话——算法由服务端配置决定，
  永不读取 token 自称。
- **Q: 强密钥有多强？** A: HS256 的密钥建议 ≥32 字节随机（RFC 7518 的
  下限），本实验用 18 词字典就能说明「短 = 零防御」的道理。
