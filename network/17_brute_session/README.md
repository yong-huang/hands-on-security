# 17 · 暴力破解与会话安全：从 0.4 秒爆出到三层防护全拦

> 爆破是用字典逐个试口令的攻击；本实验自写多线程爆破器，对 DVWA（故意布满漏洞的本地靶站）
> 的登录模块实战两端：low 档 100 条字典 0.4 秒命中；impossible 档 token + sleep
> + 锁定三层减速带，连正确口令都拦下（五连败）。顺带做一次会话固定检查
> ——本栈「登录不轮换会话 ID」的裂缝也一并讲清。所有请求只发往本地靶场。

## Background

口令是身份的唯一钥匙，而人类选口令的分布极不均匀（123456、password 类
永远是榜首）——爆破就是把这份分布变成字典逐个验证。攻击者侧要解决三件
事：并发提速（多线程）、会话与令牌跟随（每轮请求都要带有效会话）、成本
控制（限速——别打崩服务也别把自己暴露给告警）。

服务器侧的对抗则逐级出现：延迟（失败罚站几秒）、令牌（每个请求都要证明
「读过页面」）、锁定（连错几次后连对的口令也拒收）。本实验的四档靶点
（low / medium→sleep / high→token / impossible→锁定）就是这条演进线。

## What

一句话定义：**爆破是通过自动化的「尝试—反馈」循环猜出凭据**——字典是
候选集，反馈是登录页面的成功/失败差异。

心智模型：试钥匙串——一把一把插门锁，门开即停；三件防护就是让试钥匙
变慢变贵的办法：错三次门自锁（锁定）、开锁前先对暗号（token）、插错了
要缓两秒（sleep）。失效边界：爆破依赖「反馈差异」——若接口对成功/失败
统一响应且延迟恒定，在线爆破就无从判断。

| 档位 | 防护 | 爆破侧的成本变化 |
|:---|:---|:---|
| low | 无 | 100 条 0.4 秒（本机实测） |
| medium | sleep(2) | 单线程 100 条 ≥200 秒 |
| high | + token | 每轮先 GET 页面解析令牌 |
| impossible | + 锁定 | 3 次失败后 15 分钟全拒 |

## When to Use

典型场景：授权渗透里验证口令策略（弱口令普查）；给渗透报告提供「可被
爆破」的证据；给实验 19 的日志检测造真实的爆破流量样本。

何时不用：未授权目标不碰；生产环境别真打——你会把自己锁出去，验证码与
告警也会随即到场。另外，「没爆出来」不等于口令强：可能只是字典没覆盖，
或对方有锁定。

| 做法 | 机制 | 什么时候选它 |
|:---|:---|:---|
| 自写爆破器（本实验） | 会话/令牌跟随 + 线程池 + 命中即停 | 看清每条防线的成本账 |
| 专业工具（hydra 等） | 内置各协议模板与限速 | 已确认接口后的规模化验证 |
| 密码喷洒 | 一个口令横扫大量账号 | 绕开「按账号锁定」的变体 |

## Quick Start

前置：实验 12 的 DVWA 栈（本脚本自动拉起并校对时区）；Python 的
`requests`。全程约 25 秒（其中 16 秒是 impossible 的罚站）。

```bash
cd network/17_brute_session
./brute_lab.sh            # 起靶场 → 爆破演示 → 清理（约 25 秒）
./brute_lab.sh apply      # 只拉起靶场、校对时区、生成字典
./brute_lab.sh observe    # 只跑三组观察（low 爆破 / impossible 连败 / 会话检查）
./brute_lab.sh clean      # 只清 artifacts（靶场留给后续实验）
```

  ✅ 三件事各自成立：爆破可行（低档）、防住有方（impossible 连正确口令都拦）、会话需加固

诚实预期（新手第一个失败点）：① 爆破器必须跟随会话与令牌——high /
impossible 档每轮先读页面取 `user_token`，直接怼接口只会拿到 302；
② 「五连败」第 4 条是正确口令——锁定让口令失去意义；③ 锁定计时依赖 PHP
与数据库同一时区（本栈曾差 8 小时致锁定失效），脚本会自动校对。

## How It Works

![爆破的减速带](images/brute_lab.svg)

> 怎么看：从左到右是同一把字典打四档防线的成本变化（① 秒破 → ④ 拦死），
> 虚线表示「防线升级」；最右是正解——限速 + 锁定，本实验的 impossible
> 档就是它的完整示范。

> 🌐 **交互版**：本地打开 [`images/brute_lab.html`](images/brute_lab.html)。

**爆破器的三段结构**：字典循环（第 87 条埋着真口令）+ 每轮「会话与令牌
跟随」（先 GET 页面解析 `user_token`，再提交尝试）+ 命中即停。线程池让
尝试并发——本栈的 php 内置服务器有 6 个 worker，并发真的跑得起来；低档
100 条字典因此 0.4 秒见底。

**三道减速带的成本账**：sleep(2) 把单线程字典拉到 200 秒起步；token 逼
自动化每轮多读一次页面（成本 +1 请求，脚本两行就适配——它拦的是「不看
页面直接怼」的偷懒工具）；锁定最狠——3 次失败后 15 分钟连正确口令都拒，
直接清空试错预算。三者叠在一起，字典再全也打不进。

**会话固定的检查逻辑**：先建会话拿到 `PHPSESSID` → 用同一会话登录 → 看
登录后 ID 是否轮换。本栈**未轮换**：攻击者只要有办法先把一个已知 ID
塞进受害者浏览器（投毒链接、子域注入等），受害者登录后这个 ID 就成了
双方共用的有效会话。修复一行：登录成功时重新生成 ID。

**防御的正确姿势**：限速（全局计数，而不是只看单 IP）+ 锁定（账号+来源
双维度，防喷洒）+ 登录结果不泄露差异（统一文案与延迟）+ 监控告警；敏感
系统再加 MFA——两步验证之下，猜中口令也进不去。

## Pitfalls & Q&A

踩坑清单（现象 → 原因 → 解法）：

- **提交总是 302 回首页**：high / impossible 要 `user_token`——每轮先
  GET 页面拿令牌；impossible 还是 POST-only（表单方法随档位变化）。
- **锁定怎么都不触发**：计时依赖 PHP 与 DB 同时区——本栈修复前后差 8
  小时，locked 判断恒为假；对齐后锁定可复现。
- **多线程没提速**：服务端若单线程会把请求排队——并发上限在服务端
  （php -S 需 `PHP_CLI_SERVER_WORKERS`，本栈已设 6）。
- **每轮都要新会话？**：不用——但请求间必须保持同一 cookie jar，否则
  令牌与 cookie 对不上。

深入问答：

- **Q: token 为什么不能单独当爆破防御？** A: 它只逼自动化「多读一次
  页面」，适配成本约两行代码；真正的杀伤在 sleep（时间）与锁定（预算）。
- **Q: 密码喷洒是什么？** A: 「一个常见口令 × 大量账号」，每次都压在
  锁定阈值以下；对策是账号+来源双维度计数与统一失败响应。
- **Q: 为什么爆破器要提供限速选项？** A: 打崩服务等于自己制造 DoS，
  阈值型监控也在等着你——实战里「安静」比「快」更有价值。
