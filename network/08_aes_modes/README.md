# 08 · 对称加密实验室：AES-ECB/CBC/GCM 的直观对照

> 对称加密（加密解密用同一把钥匙）的底层零件只有一个：AES 把 16 字节的
> 数据块打乱。但「多块怎么串起来」（加密模式）决定了密文长什么样。本实验
> 用约 200 行代码给同一只企鹅做两份密文——ECB 轮廓清晰可辨、CBC 全噪声——
> 再演示 IV 随机性与 GCM 篡改检测。示例密钥仅限本地教学。

## Background

对称加密是最古老的加密思路（凯撒位移就是祖先）：一把钥匙把明文变密文，
再用同一把变回来。现代实现把钥匙与算法标准化成 AES，但它一次只处理
16 字节——一张图 108KB，怎么用 16 字节的零件拼出任意长度加密？

这就是「加密模式」要解决的问题。第一代答案 ECB 让每块独立加密：数学上
没错，却犯了直观错误——相同明文块变成相同密文块，「ECB 企鹅」因此成为
最著名的反例图（轮廓原样可见）。CBC 用「上一块密文参与下一块」的链式
把它打散；GCM 再进一步，用认证标签把「密文是否被篡改」管起来。

## What

一句话定义：AES 模式是**把「16 字节块加密」这个零件，串成「任意长度
消息加密」的组装方案**。

心智模型：ECB 像把拼图每片独立打乱——每片内容变了，但「哪几片长得一样」
一眼可见；CBC 像连锁反应——每片打乱前先揉进上一片的结果，图案信息随之
扩散；GCM 在连锁之外附一张防拆封条（认证标签）。失效边界：模式管不了
密钥——钥匙被盗、口令太弱，模式再高级也白搭。

两个新名词先交代：**IV**（initialization vector，初始化向量）是给 CBC 的
第一块准备的随机起始值，随密文一起明文附上——不必保密，但绝不复用；
GCM 里它叫 **nonce**（number used once，一次性随机数），规矩相同。

三种模式对照：

| 模式 | IV/Nonce | 同一明文两次加密 | 保密 | 完整性 | 结论 |
|:---|:---|:---|:---:|:---:|:---|
| ECB | 无 | 密文完全相同 | ✅ | ❌ | 多块数据禁用 |
| CBC | 随机 IV | 密文不同 | ✅ | ❌ | 旧系统常见，够用但无认证 |
| GCM | 唯一 nonce | 密文不同 | ✅ | ✅ | 新系统默认选择 |

## When to Use

典型场景：为存储/传输数据选加密模式；审计旧代码里有没有「还在用 ECB」；
理解 TLS（HTTPS 背后的传输层加密协议）与磁盘加密里为什么都换成了 AEAD
（带认证的加密，如 GCM）。

何时不用：不要自己发明协议——需要加密就用成熟封装（libsodium、
框架自带的 AEAD 接口）；GCM 对超长数据有长度上限，大文件加密用分块方案，
这些都不是手写 Cipher 实例能覆盖的场景。

| 方案 | 机制 | 什么时候选它 |
|:---|:---|:---|
| 裸模式 API（本实验） | 手动管 IV/填充/标签 | 学习与审计，读懂既有代码 |
| 框架 AEAD 封装 | 把模式与 IV 管理吃掉 | 业务代码的默认姿势 |
| libsodium（安全默认值优先的加密库） | 只暴露少量安全默认参数 | 想要「不易用错」的库 |

## How It Works

![同一只企鹅，两条加密路](images/aes_lab.svg)

> 怎么看：同一份像素走两条路——ECB 逐块独立，重复块原样泄漏（6552 个）；
> CBC 把前块密文揉进后块并用随机 IV 起步，重复块归零。两条路的终点分别是
> 「确定性可统计」与「重复模式消失」。

> 🌐 **交互版**：本地打开 [`images/aes_lab.html`](images/aes_lab.html)。

**重复块才是泄漏的燃料**：企鹅图的白色背景让 16 字节块大量重复（6552 个）。
ECB 下这些块变成同一串密文，图案轮廓因此保留；CBC 下每块都掺入前块结果，
相同明文再也不会得到相同密文。

**PKCS7 填充**：块加密要求长度是 16 的倍数。108300 补 4 字节到 108304
（`= 16×6769`）；规矩是「恰好整除也要补满一整块」，不然解密端无法区分
「末尾的填充」和「本来就有的数据」。

**IV 必须随机且唯一**：两次加密对照说明了一切——ECB 密文一致（可被统计
比对），CBC 因随机 IV 每次不同。IV 不用保密，但它一旦复用，相同的开头
明文会重新产生相同密文，历史上多起协议事故都栽在这里。

**GCM 的标签管完整性**：加密时附带 16 字节标签（可再绑一段 AAD——
「附加认证数据」，会验但不加密）；解密先验标签，改 1 字节即抛 InvalidTag。
CBC/ECB 没有这一层——密文被改了它们照样「解密成功」，输出垃圾明文。

## Pitfalls & Q&A

踩坑清单（现象 → 原因 → 解法）：

- **CBC 两次密文一致**：IV 被写死或复用——改用 `os.urandom(16)` 每次新 IV。
- **报错「data length not multiple of 16」**：忘了 PKCS7 填充——GCM 不需要，
  ECB/CBC 需要。
- **GCM nonce 复用是灾难**：同一 nonce 两次加密，两段密文相异或即得两段
  明文的差异（异或：按位运算，相同位抵消）——明文差异因此裸露。
- **不要自己拼加密**：裸模式 API 是教学入口；业务代码用框架 AEAD 封装。

深入问答：

- **Q: 为什么画企鹅？** A: 致敬「ECB 企鹅」这个流传二十年的教学梗——原图
  是 Linux 吉祥物 Tux，被 ECB 加密后轮廓依旧；本实验用代码画一只等价素材。
- **Q: ECB 一无是处吗？** A: 单块数据（恰好 16 字节、无重复结构）它没问题，
  所以 API 里保留着；但只要数据超过一块且可能有重复，就不该用。
- **Q: AES-128 还是 256？** A: 数字指密钥长度（128/256 位），两者目前都无
  实用攻击；选 256 多用于合规要求——短板永远是密钥管理与模式误用。
- **Q: CBC 的 padding oracle 是什么？** A: 攻击者通过反复提交篡改密文、
  观察「填充错误」与「其他错误」的差异，逐字节推出明文——这是 CBC 无认证的
  典型翻车方式，也是 GCM 这类 AEAD 成为默认的原因。
