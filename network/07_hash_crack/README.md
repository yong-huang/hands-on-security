# 07 · 哈希识别与口令破解器：字典攻击、规则变换与 bcrypt 成本对照

> 口令从不以明文存库——存的是它的哈希（单向摘要，算不回去的指纹）。攻击者
> 拿到库以后怎么把指纹还原成口令？本实验用约 180 行实现识别器与字典破解器：
> 无规则 8/10 → 开规则 10/10，用 hashcat 独立复核，并实测 bcrypt 单次验证
> 180ms 的成本壁垒。所有目标均为本实验自造样本。

## Background

早期系统直接存明文口令，库一泄露就等于全网账号泄露；后来改为存哈希：验证
时把输入再哈希一遍比对，数据库里不再有明文。

但「快哈希」扛不住现代算力：MD5 一秒能算三万余次，攻击升级为流水线——
字典挑常见词，规则补人性变形（首字母大写、尾加数字），逐候选求哈希查表；
彩虹表甚至预计算整表。直到 bcrypt 这类「慢哈希 + 加盐」（哈希前掺随机数据，
同一口令在不同库里哈希不同）把成本抬高四个数量级。

## What

一句话定义：哈希破解器是**把「哈希值 → 明文」的猜测过程自动化：识别算法、
生成候选、逐候选求哈希比对**的工具。

心智模型：哈希像指纹——同一口令的指纹永远相同，所以只要攒够「常见口令 →
指纹」的对照，就能反查。破解器不是「算回明文」，而是在候选空间里穷举比
对。失效边界：口令不在候选空间里（不在字典、超不出规则的变形范围），就算
一个世纪也破不出来——覆盖上限才是它的天花板。

三件套：

| 环节 | 做什么 | 本实验对应 |
|:---|:---|:---|
| 识别 | 按长度/前缀判断哈希类型 | `identify`（md5/sha1/sha256/bcrypt） |
| 候选生成 | 字典 × 规则变形 | `crack -w 字典 [-r 规则]` |
| 比对与成本 | 快哈希可穷举；慢哈希挡住 | `bench`（MD5 vs bcrypt 实测） |

## When to Use

典型场景：授权渗透中拿到哈希后的还原（先证明影响，再写进报告）；防御自查
（对自己的口令库跑一遍弱口令审计）；取证复盘（查账号是否复用了已泄露口令）。

何时不用：慢哈希 + 长口令的库别硬啃（先看 `bench` 的成本比）；在线爆破
（对着登录接口猜）是另一类问题——有锁定与限速风险，见实验 17。

| 方案 | 机制 | 什么时候选它 |
|:---|:---|:---|
| 自研破解器（本实验） | 字典 + 规则，纯 Python | 看懂原理、定制小规模审计 |
| hashcat | GPU 暴力 + 掩码（mask：按模板逐位穷举，如 ?d?d?d?d 为 4 位数字） | 大规模、已知哈希类型 |
| john (jumbo) | CPU 多格式对照 | 与 hashcat 互为印证 |

## Quick Start

前置：`pip3 install bcrypt`；hashcat 或 john（jumbo 版）可选，装上自动对照。

```bash
cd network/07_hash_crack
./hash_cracker.sh              # 造样本 → 识别 → 破解 → 对照 → 成本实测（约 5 秒）
./hash_cracker.sh apply        # 只生成目标（10 个 MD5 + 1 个 bcrypt）
./hash_cracker.sh observe      # 只跑识别/破解/对照/实测
./hash_cracker.sh clean        # 清理 artifacts/
```

诚实预期（新手第一个失败点）：bcrypt 目标**不参与字典攻击**是设计行为——
每次验证 180ms，全字典要试到天亮（`bench` 就是它的成本说明书）；hashcat
首次运行要做内核编译，可能多等十几秒，之后是秒级。

## How It Works

![口令破解流水线](images/hash_cracker.svg)

> 怎么看：字典经规则变换放大成候选流，逐候选过快哈希并比对；bcrypt 走的是
> 同一批候选，成本高数千倍，直接落入「未破项」——这条暗线就是慢哈希的
> 防御价值。

> 🌐 **交互版**：本地打开 [`images/hash_cracker.html`](images/hash_cracker.html)。

**识别先于破解**：类型不同算法不同。识别只靠形状：32 位十六进制→MD5、
40→SHA1、64→SHA256、`$2b$12$` 前缀→bcrypt（cost=12）。

**规则是「人性放大器」**：每个字典词展开成 18 个变形——原样、大小写、
`capitalize()+尾数字` 等。`Password1` 就是 `password` 的首字母大写加 `1`，
`MONKEY` 是 `monkey` 全大写：两个都没有直出字典，却被规则一击命中。

**快慢哈希的鸿沟**：MD5 单次 ~29µs，bcrypt(cost=12) 单次 ~180ms，实测比值
约 6000 倍（每次运行数值有波动，见输出块）；cost 每 +1，耗时与攻击成本
同步翻倍。加上每人独立的随机盐，同一口令在不同库里指纹不同——预计算表
（彩虹表）整体报废。

**对照与验收**：本机 Homebrew 的 john 是 plain 1.9（不支持 raw-md5），脚本
自动降级用 hashcat 完成对照：同一字典还原 dragon/letmein，与自研结果逐条
一致；装了 john-jumbo 则自动切换（`--list=formats` 探测能力）。

## Pitfalls & Q&A

踩坑清单（现象 → 原因 → 解法）：

- **缺少 bcrypt**：`pip3 install bcrypt`；只在生成/验证慢哈希时需要它。
- **hashcat 报 no devices**：虚拟机或驱动不匹配时加 `--force`，或装
  john-jumbo 走 CPU。
- **破解数不到 100%**：候选空间（字典×规则）覆盖不到的口令注定破不出——
  这正是「长随机口令 + 慢哈希」的防御原理。
- **时间统计接近 0.00s**：25 词 × 450 候选规模太小；真实字典是千万级词表，
  所以成熟工具走向 GPU 与掩码枚举。

深入问答：

- **Q: 为什么不直接暴力枚举所有口令？** A: 8 位随机口令的搜索空间是 10¹⁴
  量级，字典+规则是在「真实人类选口令的习惯分布」里抄近路——先抄习惯，
  再谈算力。
- **Q: 加盐解决了什么？** A: 让「同一口令 → 同一指纹」变成「每库每人不同」，
  摧毁预计算表；但它不增加单次尝试成本，所以还要配合慢哈希。
- **Q: 拿到哈希之后做什么才不算白干？** A: 证明影响：用还原出的口令验证它
  能登录什么（授权范围内），并在报告里给出「改密 + 存 bcrypt + 弱口令黑名单」
  的修复项。
- **Q: 自己练这个有法律风险吗？** A: 攻击对象只能是自己的样本或书面授权的
  系统；破解他人泄露库同样违法——「数据已经泄露」不构成授权。
