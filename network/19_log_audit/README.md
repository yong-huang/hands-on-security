# 19 · 日志审计与爆破检测器：滑动窗口、规则引擎与实战日志对账

> 换到蓝队视角：日志是攻击唯一绕不开的现场记录。本实验写一个日志审计器
> ——解析三种日志格式（ssh 的 auth.log、Apache access、PHP 容器日志），
> 用滑动窗口数爆破、用规则引擎分拣「扫描器 / 注入 / 穿越 / XSS」特征，
> 输出告警与 Markdown 审计报告；再用 awk 手工统计逐条对账，最后拿真实
> DVWA（故意布满漏洞的本地练习靶站）的注入流量检出 SQL 注入 URI 特征。合成与自建，全部本地。

## Background

攻击有两样藏不住：**频率**与**特征**。爆破是登录窗口里的高频失败；
扫描器的 UA（User-Agent：请求头里客户端自我标识的字段，扫描器常忘了
伪装它）与 404 扫荡、注入的 `UNION SELECT`、穿越的 `../`，都写在请求行。

三类日志各有视角：auth.log 记「谁在登」、access.log 记「谁在请求什么」、
应用容器日志记「进程眼里的世界」。

问题在于量：人看不过来，于是需要机器分拣——解析、按规则挑、出结论。
这也是实验 6 的报告对账思路的延续：先能手工算出来，才配相信自动化的数。

## What

一句话定义：**日志审计器是「解析 → 规则 → 输出」的流水线**——把多格式
日志变成结构化事件，按频率与特征挑出可疑行为，输出告警与报告。

心智模型：分拣中心——三路包裹（日志）进场，先按面单格式分类（解析），
再对照违禁清单（规则）挑出可疑件，最后出告警单和日报（报告）。

失效边界：规则只认识「写下来的形状」——低频慢速的密码喷洒（一个常见
口令横扫大量账号）、藏在正常 UA 里的探测、被篡改或缺失的日志，都会从
网眼漏过去。

本实验的规则清单（R1–R6，可扩展）：

| 规则 | 信号 | 样张表现 |
|:---|:---|:---|
| R1 爆破 | 60 秒窗口失败 ≥30 次 | 植入 IP：50 次 |
| R2 扫描器 UA | sqlmap/gobuster 等指纹 | 两个 IP 各中一次 |
| R3 注入特征 | URI 含 union select / or 1=1 | 9 条请求 |
| R4 路径穿越 | URI 含 `../` | 实战 LFI 请求 |
| R5 XSS 特征 | URI 含 `<script` | 实战 XSS 请求 |
| R6 爆破后成功 | ≥10 次失败后有 Accepted | 植入 IP 登录成功 |

## When to Use

典型场景：值守与事故复盘（先跑一遍规则清单定性）；把自己渗透实验的
流量回灌进检测器，看防守方眼里的样子；日志合规审计的最小可用集。

何时不用：数据量到每秒数万行时，上专业日志栈（ELK / Splunk）而不是
自写脚本——但自写的价值是**知道自己在找什么**，再用专业工具把它放大。

| 做法 | 机制 | 什么时候选它 |
|:---|:---|:---|
| 自写审计器（本实验） | 解析 + 规则 + 报告全流程 | 看清检测的每个零件 |
| grep/awk 手排 | 临时组合命令 | 单次小量排查、对账基准 |
| 专业 SIEM | 采集/索引/告警平台 | 生产级规模与留存 |

诚实预期（新手第一个失败点）：① 合成日志是「带答案的考试」——植入与
负对照写死，检出结果可验证；② Top10 对账必须**逐条 diff**：计数口径、
排序并列都算不一致；③ 实战检出依赖容器日志窗口（本地做法；生产里对应
集中式日志平台）。

## How It Works

![日志分拣流水线](images/log_audit.svg)

> 怎么看：从左到右是「三路日志 → 行解析器 → 规则引擎 → 告警与报告」，
> 最右的虚线回边是响应闭环；中间两个标签对应两种检测法——窗口（频率）
> 与特征（形状）。

> 🌐 **交互版**：本地打开 [`images/log_audit.html`](images/log_audit.html)。

**三路日志，三种格式**：auth 行形如
`May  1 03:05:00 labhost sshd[2001]: Failed password for admin …`；
Apache 行含请求行 + 状态码 + UA；容器行是
`[8] [Wed …] ip:port [302]: GET /uri`。

解析器**逐行独立判别**（依次试三条正则），不认识的行直接跳过、不计入
事件——混合喂日志也不会串味。

**滑动窗口：为什么不是整点统计**：爆破不会挑整点。要看「**任意** 60 秒
内最多的失败数」——时间排序后双指针一次扫描（O(n)）：左指针随右指针
推进，把超出窗口的头部弹出去。窗口与阈值就是告警系统的灵敏度旋钮：调
大漏报少误报多，调小反之。

**带答案的考试**：植入 `203.0.113.66`——1 分钟内 50 次失败（R1）+ 随后
登录成功（R6）+ sqlmap UA（R2）+ 9 条注入 URI（R3）；负对照
`198.51.100.23` 只有 8 次散落失败，必须一声不响。检出「4 条命中、
0 误报」才算这堂课及格。

**从报告到闭环**：Markdown 报告四节——结论摘要 / 规则命中 / Top10 /
建议动作；建议动作要落到真实处置（封禁、复查口令、把注入特征加进规则）
——实验 20-21 会把这里的特征落成 IDS（Intrusion Detection System：入侵检测系统）规则。

## Pitfalls & Q&A

踩坑清单（现象 → 原因 → 解法）：

- **Top10 对不上但「看着差不多」**：排序并列时两边次序可能不同——让
  计数互不相同（生成器保证），并逐条 diff 而不是数个数。
- **窗口边界差一条**：恰在第 60 秒的事件属于「下一个窗口」——实现里用
  左闭右开判定（差值 ≥ 窗口就弹左指针）。
- **实战日志混入旧流量**：`docker logs` 取窗口前先留沉淀时间（本实验
  先 sleep 再取），否则上一波流量会混进来。
- **格式判别误吞行**：别用「文件级」判别格式——按行独立判别，不认识的行
  直接跳过，比乱猜安全。

深入问答：

- **Q: 检测到爆破之后呢？** A: 分级响应——告警 → 人工复核 → 封禁 →
  复盘加固；报告停在「发现了」就是没写完，要给出动作建议。
- **Q: 阈值能拦住「慢攻击」吗？** A: 拦不住——低于阈值就是设计好的
  网眼（实验 17 的密码喷洒即是）；检测侧的对策是账号+来源双维度计数
  与长期基线，没有单一开关。
- **Q: 日志被攻击者清掉怎么办？** A: 异地集中收集、只追加存储、哈希
  校验；本地日志只够演练——实验 23 的应急响应会回到这一课。
